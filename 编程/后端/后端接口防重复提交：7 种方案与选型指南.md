# 后端接口防重复提交：7 种方案与选型指南

> 原文链接：[不知理义生于不学](https://mp.weixin.qq.com/s/_R4MQGBDiXXni4TH37NhQg)

---

## 一、为什么重复提交问题"阴魂不散"？

重复提交的四大诱因：

| 诱因 | 典型场景 | 危害等级 |
|------|---------|---------|
| 前端误操作 | 用户双击按钮、快速刷新页面 | 一般 |
| 网络不稳定 | 延迟、抖动、丢包，客户端误判请求失败并重发 | 较高 |
| 系统自动重试 | HTTP 客户端超时重试、RPC 框架的 Failover 机制 | 高 |
| 消息重复消费 | MQ 中间件消息投递至少一次（at-least-once）语义 | 极高 |

**重复提交的三大后果：**

1. **资金风险**：重复入账、重复扣款——充值一笔钱，后台入账两次，月底对账时才发现
2. **数据一致性崩溃**：数据库出现脏数据，订单表里同一个交易号对应两条记录，下游系统跟着出问题
3. **用户体验雪崩**：用户收到两次"充值成功"的推送、客服工单激增、信任度下降

## 二、防重复提交的本质

**幂等性（Idempotence）**：同一操作执行一次或多次，对系统状态的影响一致。这是数学概念，是系统对外的承诺。

**防重复提交**：防止同一个请求在短时间内被多次处理。是工程手段。

> 幂等性是目标，防重复提交是实现手段之一。

核心要解决两个问题：
1. **如何判断两次请求是不是"同一个请求"？** → 需要唯一的标识
2. **如何保证"同一个请求"只处理一次？** → 需要某种约束机制

## 三、7 种武器：从轻到重逐层防御

### 武器 1：前端按钮防抖（第一道门槛）

```javascript
function debounce(fn, delay = 500) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  }
}
```

- **原理**：用户点击提交按钮后，在指定时间（如 500ms）内忽略后续点击；也可以直接在点击后将按钮设为 disabled
- **适用场景**：表单提交、搜索框输入
- **局限**：恶意用户绕过前端直接调接口，这层防护形同虚设。**前端防重只是锦上添花，后端防重才是雪中送炭**

---

### 武器 2：数据库唯一约束（最可靠的兜底）

```sql
-- 为业务关键字段添加唯一索引
ALTER TABLE recharge_record
ADD UNIQUE INDEX uk_trans_proof (trans_proof);
```

```java
try {
    rechargeRecordService.save(record);
} catch (DuplicateKeyException e) {
    return Result.error("请勿重复提交");
}
```

- **优点**：最可靠，即使 Redis 挂了、应用重启了，这层防护依然在
- **局限**：修改表结构需要 DBA 配合；异常处理路径不够优雅；高并发下唯一约束冲突会影响数据库性能

---

### 武器 3：Redis 请求指纹去重（最常用的快速拦截）

核心思路：用业务唯一标识（如交易凭证号）生成一个 Redis Key，利用 `setIfAbsent`（即 SETNX）的原子性，在短时间内拦截重复请求。

```java
@Autowired
private RedisTemplate<String, Object> redisTemplate;

@PostMapping("/recharge")
public Result<String> recharge(@RequestBody RechargeRecord record) {
    // 生成请求指纹
    String requestKey = "recharge:duplicate:" + record.getTransProof();
    // 10秒内同一凭证只能提交一次
    Boolean isFirst = redisTemplate.opsForValue()
        .setIfAbsent(requestKey, "1", 10, TimeUnit.SECONDS);
    if (Boolean.TRUE.equals(isFirst)) {
        return rechargeService.saveRecord(record);
    } else {
        return Result.error("请勿重复提交");
    }
}
```

**为什么推荐？**
- 不需要修改表结构
- SETNX 是原子操作，天然支持并发
- Redis 的性能远高于数据库
- 过期时间自动清理，不会无限膨胀

> Key 的 TTL 时间要合理设置——太短可能拦不住重试，太长会占用内存。一般建议 3~10 秒。

---

### 武器 4：幂等令牌（Token 机制）

互联网公司最经典的方案之一，尤其适合表单提交类场景。

**流程分三步：**

1. 客户端请求 → `GET /api/token` → 后端生成 Token 存入 Redis → 返回给客户端
2. 客户端提交表单 → `POST /api/order`（携带 Token）→ 后端验证 Token
3. 后端从 Redis **原子删除** Token → 删除成功 = 首次请求 → 删除失败 = 重复请求

> 关键点：为什么是"删除"而不是"查询"？因为 DELETE 是原子操作——多个并发请求只有一个能成功删除，天然解决并发竞态问题。

**进阶**：通过自定义 `@Idempotent` 注解 + AOP，可以把这个逻辑做成通用组件，一行注解就能给任意接口加上防重能力。

---

### 武器 5：防重表 + AOP（工程化的通用方案）

适用于系统中有很多接口都需要防重的场景。

```sql
CREATE TABLE idempotent_record (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    unique_key  VARCHAR(128) NOT NULL COMMENT '幂等唯一标识',
    status      TINYINT NOT NULL DEFAULT 0 COMMENT '0-处理中 1-已完成',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expire_time DATETIME NOT NULL COMMENT '过期时间',
    UNIQUE INDEX uk_unique_key (unique_key)
) COMMENT '接口防重表';
```

```java
// 一行注解，完成防重
@Idempotent(uniqueKeyExpression = "#request.orderId")
@PostMapping("/order/create")
public Result createOrder(@RequestBody OrderRequest request) {
    return orderService.create(request);
}
```

AOP 切面自动完成：提取幂等 Key → 插入防重表 → 检查唯一约束 → 放行或拦截。

**优势**：
- **声明式**：业务代码零侵入
- **可追溯**：防重记录持久化在数据库，方便排查问题
- **可扩展**：`IdempotentProcessor` 接口化设计，可切换为 Redis 实现或其他存储

### 武器 6：分布式锁（高并发场景的利器）

当并发量上来后，Redis 的 SETNX 可能不够用——比如需要对同一笔交易锁定更长时间，或者需要在加锁期间执行多个操作。

```java
@Autowired
private RedissonClient redissonClient;

public Result saveRecord(RechargeRecord record) {
    String lockKey = "rechargeLock:" + record.getTransProof();
    RLock lock = redissonClient.getLock(lockKey);
    try {
        // 等待5秒，锁持有10秒
        if (lock.tryLock(5, 10, TimeUnit.SECONDS)) {
            if (duplicateCheck(record.getTransProof())) {
                return Result.error("重复提交");
            }
            return doSave(record);
        }
        return Result.error("系统繁忙，请稍后重试");
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

- **适用场景**：分布式微服务架构下，多个服务实例可能同时收到同一笔交易的请求
- **选型建议**：如果项目已经集成了 Redisson，优先用它。不要手写 Redis 分布式锁——Redisson 内置了看门狗续约、锁可重入等高级特性

---

### 武器 7：乐观锁 / 状态机（更新操作的防重）

前面几种方案主要针对"新增"操作。防止重复更新，乐观锁和状态机是更好的选择。

**乐观锁（版本号机制）：**

```sql
-- 第一次更新成功：version 0 → 1
UPDATE order SET status = 2, version = version + 1
WHERE id = 123 AND version = 0;

-- 重复请求：version 已经是 1，条件不匹配，影响行数 = 0
UPDATE order SET status = 2, version = version + 1
WHERE id = 123 AND version = 0;
```

**状态机机制（更适合有业务含义的场景）：**

```sql
-- 订单状态只能从"待支付"变为"已支付"
UPDATE order SET status = 'PAID'
WHERE order_id = 123 AND status = 'UNPAID';

-- 重复请求时 status 已经是 'PAID'，WHERE 条件不匹配，自然失败
```

- **优势**：不需要引入额外组件，完全利用数据库自身能力
- **局限**：只适用于"更新"场景，且表结构需要预留状态字段或版本号字段

## 四、方案选型指南

| 你的场景 | 推荐方案 | 理由 |
|---------|---------|------|
| 简单表单提交 | 前端防抖 + Redis 指纹去重 | 成本最低，效果足够 |
| 支付/充值等资金场景 | Redis 指纹去重 + 数据库唯一约束 | 双重保障，缺一不可 |
| 多接口统一防重 | 防重表 + @Idempotent 注解 | 一次开发，到处使用 |
| 分布式微服务 | 分布式锁 + 幂等令牌 | 跨实例也能防重 |
| 更新操作防重 | 乐观锁 / 状态机 | 轻量级，不依赖外部组件 |
| 消息队列消费 | 消费记录表 + 唯一索引 | 保证消息只处理一次 |

---

## 五、最佳实践："快慢双保险"方案

```
请求进入
   ↓
[快速拦截层] Redis SETNX 检查请求指纹（3~10秒TTL）
   ├── 命中 → 直接返回"请勿重复提交"
   └── 未命中 ↓
[业务处理层] 执行业务逻辑
   ↓
[持久保障层] 数据库唯一约束兜底
   ├── 成功 → 正常返回
   └── 冲突 → 返回重复提交提示（兜住了Redis漏网之鱼）
```

> 这就像你家的防盗门（Redis）+ 保险柜（数据库唯一约束）。门坏了还有柜子，双重保险才能安心睡觉。

## 六、容易被忽略的细节

### 6.1 Key 的设计要足够精确

```java
// ❌ 错误：太粗，同一用户所有请求都会互斥
String key = "lock:" + userId;

// ❌ 错误：太细，不同金额的同笔交易被视为不同请求
String key = "lock:" + userId + ":" + amount;

// ✅ 正确：恰到好处，用业务唯一标识
String key = "lock:" + transProof;
```

### 6.2 TTL 设置要有依据

不要拍脑袋定时间，根据业务流程的最大耗时来设置：
- 普通 CRUD 接口：3~5 秒
- 涉及第三方调用（支付网关、银行接口）：30~60 秒
- 异步任务类接口：根据任务预期完成时间设定

### 6.3 失败后的清理策略

```java
try {
    doBusiness(record);
} catch (Exception e) {
    // 业务失败，释放防重Key，允许用户重试
    redisTemplate.delete(requestKey);
    throw e;
}
```

### 6.4 幂等性不是免费的午餐

引入幂等有代价：并行执行改为串行会降低吞吐量，额外逻辑增加系统复杂度。

> **查询接口天然幂等，无需额外处理；只有写操作接口才需要考虑防重。非必要不引入。**
