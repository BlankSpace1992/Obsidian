# 如何设计一个灰度发布系统？

> 原文链接：[中年失业程序员](https://mp.weixin.qq.com/s/DQmqXCNibJQyB7cCXxiOsw)

---

## 核心认知

真正的企业级灰度发布，绝非简单的 IP 流量切割，而是围绕三大核心能力搭建：

```
精准分流 → 全链路染色 → 无损回滚
   ↓            ↓            ↓
用户一致性    调用闭环    故障兜底
```

三者缺一不可。

---

## 一、精准分流：基于用户 ID 一致哈希

> IP 分流是入门级劣解——动态 IP、多终端差异都会导致用户频繁切换新旧版本。

### 正确方案

| 组件 | 职责 |
|------|------|
| **Spring Cloud Gateway** | 自定义灰度过滤器，解析 Token 内用户 ID |
| **Nacos 配置中心** | 存储灰度配比，动态调整无需重启 |
| **取模算法** | `userId % 100 < 5` → 命中灰度的用户固定进新版 |

### 实战流程

```
灰度比例 5% → 用户 ID 对 100 取模 < 5 → 固定路由新版
监控下单成功率平稳 → 上调至 20% → 50% → 100%
配置修改即时生效，无需重启网关
```

> 核心保证：**同一个用户，永久路由至同一服务版本**，彻底杜绝版本来回切换。

---

## 二、全链路流量染色

> 仅完成网关分流远远不够。必须保证灰度用户整条调用链路统一执行新版本逻辑。

### 同步链路

```
网关植入 X-grey-tag=true
        ↓
拦截器透传至订单、支付、库存等下游服务
        ↓
全链路调用新版接口
```

### 异步链路（最容易遗漏）

```
用户下单 → MQ 库存扣减消息
              ↓
灰度标记同步写入消息 Header
              ↓
库存消费端识别标记 → 扣减新版库存
```

> 如果漏掉异步链路染色：前端新版下单 → 后端旧版扣库存 → **库存对账错误**。

---

## 三、无损回滚 + 数据兼容

### 回滚架构原则

**旧版本服务实例永久保留，新版本独立部署、资源隔离。**

```
新版支付超时率飙升
        ↓
Nacos 将灰度比例改为 0（1 秒生效）
        ↓
全量切回旧版支付链路
        ↓
无需停机删服务
```

### 数据库向前兼容

| ✅ 可以做 | ❌ 不能做 |
|----------|----------|
| 新增字段（旧版自动忽略） | 修改原有字段类型 |
| 新表 | 改旧表结构 |

> 新版结算仅新增 `积分抵扣` 字段，旧版自动忽略该字段读写；严禁修改原有 `支付金额` 字段类型，保证新旧服务均可正常读写订单数据。

---

## 总结

| 核心能力 | 手段 | 解决的问题 |
|---------|------|-----------|
| **精准分流** | 用户 ID 哈希 + Nacos 动态配比 | 同一用户不会跳版本 |
| **全链路染色** | `X-grey-tag` 透传 + MQ Header | 同步/异步链路统一走新版 |
| **无损回滚** | 旧版实例保留 + DB 向前兼容 | 一秒切回旧版，数据兼容 |

> 摒弃浅层流量分流思维，围绕三大核心能力搭建系统，才能满足线上业务**低风险、可回撤、高稳定**的迭代上线需求。
