# 消息队列选型：Kafka、RocketMQ、RabbitMQ，我们最后选了哪个，为什么？

> 原文链接：[北哥](https://mp.weixin.qq.com/s/ZtaysWEvIQli62Dami5-JA)

---

## 选型最大的坑

> 先看产品特性，再往自己业务上套。正确顺序是反过来的——**先把业务场景、核心诉求写出来，再对照产品。**

---

## 第一步：把需求写下来

示例业务场景：
- 订单状态变更通知下游（支付完成 → 通知物流、积分、库存）
- 延迟消息（下单 30 分钟未支付，自动取消）
- 日志异步写入（操作日志不走主流程，异步落库）
- 日均消息量：百万级

| 维度 | 要求 | 权重 |
|------|------|------|
| 消息可靠性 | 不能丢，需要重试机制 | 高 |
| 延迟消息 | 必须支持，核心业务需求 | 高 |
| 事务消息 | 最好支持，解决分布式事务 | 高 |
| 吞吐量 | 百万级/天，不是极端场景 | 中 |
| 运维成本 | 小团队，没有专职运维 MQ | 高 |
| 学习成本 | 团队大部分人没深入用过 MQ | 中 |

---

## 三个候选者

### RabbitMQ

老牌 MQ，2007 年就出来了。

- **优势**：延迟极低（微秒级）、路由规则最灵活（Exchange + Binding）、管理界面友好、社区成熟
- **劣势**：吞吐量上限相对低（万级/秒）、Erlang 实现导致深层问题排查困难、延迟消息需通过死信队列 + TTL 模拟
- **适合**：消息量不大、路由规则复杂、运维资源充足

### Kafka

大数据领域事实标准，LinkedIn 出品。

- **优势**：吞吐量极高（百万级/秒）、持久化设计好、与 Flink/Spark 生态无缝集成
- **劣势**：**不支持延迟消息（硬伤）**、功能偏底层（无死信队列、消费重试需自己实现）、运维复杂（需专人维护）
- **适合**：日志收集、大数据流处理、超高吞吐、有专职运维

### RocketMQ

阿里 2012 年开源，专门为电商业务消息场景设计。

- **优势**：**原生支持延迟消息**（18 个延迟级别）、**原生支持事务消息**（半事务消息 + 回查机制）、消费失败自动重试（默认 16 次阶梯式）、死信队列内置、Java 实现
- **劣势**：非 Java 生态支持弱、社区活跃度不如 Kafka/RabbitMQ、NameServer 概念需一定时间理解
- **适合**：业务消息场景、Java 技术栈、需要延迟消息和事务消息

## 核心差异对比

| 特性 | RabbitMQ | Kafka | RocketMQ |
|------|----------|-------|----------|
| 吞吐量 | 万级/秒 | 百万级/秒 | 十万级/秒 |
| 消息延迟 | 微秒级 | 毫秒级 | 毫秒级 |
| 延迟消息 | 需插件模拟 | ❌ 不支持 | ✅ 原生 18 级 |
| 事务消息 | ❌ | ❌（方案复杂） | ✅ 原生支持 |
| 消费重试 | 需自行实现 | 需自行实现 | ✅ 默认 16 次 |
| 死信队列 | 需配置 | ❌ | ✅ 自动进入 |
| 运维难度 | 低 | 高 | 中 |
| 开源语言 | Erlang | Scala/Java | Java |
| 适用场景 | 复杂路由/低延迟 | 大数据/日志 | 业务消息/电商 |

## 决策过程

### 第一步：排除 Kafka

有延迟消息需求（下单 30 分钟未支付自动取消），Kafka 原生不支持。要自己实现需要延迟 topic 加消费者轮询，代码复杂度高，不值得。

### 第二步：RabbitMQ vs RocketMQ

最核心的三个需求：**延迟消息、事务消息、消费重试**。

| 需求 | RocketMQ | RabbitMQ |
|------|----------|----------|
| 延迟消息 | 18 个级别，一行配置搞定 | TTL Queue → 死信队列 → 消费，绕三层 |
| 事务消息 | 直接支持 | 需自己实现本地消息表 + 重试 |
| 消费重试 | 内置阶梯式，16 次后进死信 | 需自己处理 |

### 第三步：团队匹配度

团队全 Java 栈，RocketMQ 是 Java 写的，遇到问题可以看源码。中文文档、论坛丰富，问题排查方便。

> **最终选择：RocketMQ**

## 上线后踩的坑

### 坑一：NameServer 地址没配全

```properties
# 多个地址用分号分隔
rocketmq.name-server=192.168.1.1:9876;192.168.1.2:9876
```

只配一个时，NameServer 重启期间生产者报连不上。

### 坑二：消费者线程数没调

```java
consumer.setConsumeThreadMin(20);
consumer.setConsumeThreadMax(64);
```

默认 20 线程，消息量起来后堆积，增加到 64 恢复正常。

### 坑三：延迟消息级别是固定的

RocketMQ 延迟级别只有预设 18 个（1s ~ 2h），不支持任意秒级延迟。如需精确到秒，要用 Redis ZSet 或商业版。

---

## 选型 Checklist

- [ ] 有没有延迟消息需求？有 → 直接排除 Kafka
- [ ] 有没有事务消息需求？RabbitMQ 原生不支持
- [ ] 团队规模多大？Kafka 运维成本高，小团队慎重
- [ ] 消息量级是多少？百万级/天 vs 百万级/秒，差距很大
- [ ] 主要技术栈是什么？语言不匹配会导致客户端支持差

---

> 没有最好的 MQ，只有最适合你场景的。先排除不满足核心需求的，再在剩下的里面比运维成本和团队匹配度。
