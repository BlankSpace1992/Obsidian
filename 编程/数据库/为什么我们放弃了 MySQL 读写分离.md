# 为什么我们放弃了 MySQL 读写分离

> 原文链接：[BiggerBoy](https://mp.weixin.qq.com/s/HoYb9Z6UOgbzpQxE_oITFQ)

---

## 背景

2019 年，MySQL 主从架构扛了一整年：读 QPS 8000，写 QPS 2000，两台从库，CPU 稳定在 40% 以下。

2020 年做了一个决定：**下掉读写分离，全量走主库。**

---

## 坑一：主从延迟

**场景**：下单后立刻跳转订单详情页。

```
用户下单（写主库）
  ↓ 重定向
订单详情页（读从库）← 50ms~2s 的主从延迟

用户下单完看不到订单 → 客诉
```

**解决方案**：写完后 30 秒内强制读主库。

```java
afterWrite(orderId) {
    forceReadMasterCache.put(orderId, true, 30, SECONDS);
}

readOrder(orderId) {
    if (forceReadMasterCache.get(orderId)) {
        return masterDB.query(orderId);
    }
    return slaveDB.query(orderId);
}
```

客诉基本消失，但**代码里到处都是"强制读主"的逻辑**，后来数了一下，一共 **17 处**。

---

## 坑二：慢 SQL 扩散

一个报表查询跑 GROUP BY，耗时约 8 秒。

- 读写分离前：慢查询只影响主库，晚上跑可接受
- 读写分离后：被路由到从库，8 秒查询**堵住了从库连接池**

结果：用户查订单列表从 20ms 暴涨到 3 秒。

**解决方案**：慢查询单独用一个只读实例，但引入了更多数据库实例，运维成本上升。

---

## 坑三：中间件升级踩坑

使用 Sharding-Sphere-JDBC 4.x，升级到 5.x 时 API 全变。

- 升级花了两周，改了约 40 个配置文件
- 上线后出现 bug：读从库失败时**没降级到主库**
- 线上跑了三天才发现，每天约 **千分之三** 的订单详情请求失败

---

## 放弃读写分离后：升级主库

直接升级硬件 + 连接池优化。

| 方案 | 成本 | 延迟问题 | 运维复杂度 |
|------|------|---------|-----------|
| 读写分离（旧） | 2 台从库 | 有，需强制读主 | 高（17 处代码 + 中间件维护） |
| 升级主库（新） | 1 台 256G 内存主库 | 无 | 低（单机强一致） |

主库从 16 核 64G 升到 256G 内存 + 多地高可用，缓存命中率从 70% 提到 95%。

---

## 两个判断标准

读写分离不是不好，关键看业务体量：

1. **读 QPS 是否超过单主库上限？** → 8000 QPS，升配后单主轻松扛 2 万，不需要分离
2. **是否有强一致性读场景？** → 下单后立刻读，占 30% 读流量，享受不到分离红利

> 两个条件有一个不满足，读写分离带来的复杂度可能大过收益。
